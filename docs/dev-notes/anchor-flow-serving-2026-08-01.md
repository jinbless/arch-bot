## 2. 정기 칸은 조건부 칸이고, 근거가 4단계다

배선하고 재측정하니 "안전검사 대상 아님 = 정기 칸 빈다"는 **틀렸다**.

| 정기 근거 | 종 수 | 예 |
|---|---|---|
| 안전검사 + 가이드 | 2 | 프레스등, 로봇 |
| 안전검사(법정 주기·검사기준) | 6 | 크레인, 이동식 크레인, 리프트, 곤돌라, 고소작업대, 컨베이어등 |
| **가이드만**(권고) | 1 | **지게차** — 정기점검 절차 6건 |
| 없음 | 10 | 공기압축기, 슬링, 차량계 건설기계 등 |

→ **법정과 권고를 같은 칸에 섞으면 안 된다.** 안전검사는 안 받으면 위법이고 주기가 정해져 있지만
가이드 정기점검은 권고다. `flow_slice_all.json`의 `inspection.periodic_source` 4값으로 기록되고,
화면에서 `법정`/`권고` 배지로 갈린다.

## 3. ★ 앵커 좌표 버그 — 같은 유형 5번째

`measure_anchor_accuracy.py`가 좌표를 `(절, 관)`으로만 비교하고 **편·장을 버렸다.**
규칙에는 `절1`이라는 이름의 절이 **20곳** 있다(편2장1 기계 일반기준 / 편2장3 전기 / 편3 각 장 통칙 …).

| 지표 | 초판(부풀림) | **정정** |
|---|---|---|
| 관 단위 정확 일치 | 0.778 | **0.711** |
| 절 단위 일치 | 0.800 | **0.733** |
| 완전 오인식 | 20% | **26.7%** |

- **서빙 경로는 무영향** — `cue_article_service`는 `group_keys` 문자열로 직접 조회하고 좌표 비교를 안 한다
- 재발 감지용으로 산출물에 `legacy_exact_match`(구 방식)를 함께 남겼다
- 정본은 `docs/status/evaluation-baseline.md`의 '앵커 인식 정확도' 절

**재발 이력**: `join_coverage.py` → `build_flow_slice_all.py` → 흐름 커버리지 측정 →
`measure_anchor_accuracy.py` → **gimulmul_index 카탈로그 자체**(아래 §4).
증상이 매번 같다 — **숫자는 좋아 보이는데 내용이 틀린다.** 지표가 예상보다 좋으면 좌표부터 의심할 것.

## 4. 흐름 인덱스를 127종으로 — 커버리지 100%, 그러나 얇다

별표 3은 원래 '작업 시작 전 점검' 칸 **하나의 재료**인데 전체 목록 노릇을 하고 있었다.
앵커(RESOLVE)는 `group_keys`를 내므로 인덱스도 그룹이어야 짝이 맞는다.

- 정답 기준 흐름 커버리지 **57.8% → 100%**(감독관 gold 45장), 항목 704 → 1,989개
- 이름도 제대로 붙는다: 분전함 사진에 '이동식 방폭구조 전기기계·기구를 사용할 때'(별표 3 행 이름) 대신
  '전기 기계ㆍ기구 등으로 인한 위험 방지'(그룹 이름)

계획·인적·작업전은 총칙(제38·39·35조)을 전 그룹에 1건씩 주입하므로 무조건 찬다.

| 칸 | 겉보기 | **실질**(총칙 주입 제외) |
|---|---|---|
| 계획 | 100% | **13%** |
| 인적 | 100% | **17%** |
| 작업 전 | 99% | **20%** |
| 작업 중 | 99% | 99% |
| 종료 | 25% | 25% |

**실질 1칸짜리가 68종**이다. 절반 이상이 '작업 중'만 있는 얇은 흐름이다.

### 카탈로그 자체의 좌표 뭉갬(미해결)

`gimulmul_index.json`의 그룹키에 편·장이 없어 **`절1 통칙` 하나에 편3의 12개 장 통칙이 합쳐져** 있었다
(3그룹·37조문, 전부 편3 보건). 공유 카탈로그를 고치면 서빙(RESOLVE 카탈로그·alias·임베딩)까지
파급되므로 **흐름 조립 단계에서만** 좌표별로 쪼갰다(113 → 127종). **카탈로그 자체 수정은 남은 과제.**

### 이름 매칭은 불확실하다는 걸 드러낸다

앞 4글자 매칭이 '그 밖의'·'설비의' 같은 조각에 걸려 오부착했고(유해인자←궤도설비, 비계←타워크레인),
전체 일치로 조이니 누락이 생겼다(화학설비·전기작업·해체작업·입환작업).
→ 꼬리 상투어를 떼고 `ㆍ/및`로 쪼갠 조각까지 후보로 쓰되 3글자 미만은 버린다.
그래도 불확실하므로 출처를 `별표 4(이름매칭)`·`별표 2(이름매칭)`로 표기해 좌표 매칭과 구별한다.

## 5. 서빙 배선 — 플래그 off 기본

`flow_service.py` + `WorkFlowPanel.tsx`. 실제 지게차 사진으로 end-to-end 검증:
앵커 `차량계 하역운반기계등 > 지게차` 정확 인식, 6칸 59건, 대안 2개.

- **RESOLVE 공유**: `cue_article_service.resolve()`에 장면 단위 memo(최대 32). 따로 부르면 비용 2배일 뿐
  아니라 **조문 후보와 흐름이 서로 다른 기인물을 가리키는** 더 나쁜 결과가 난다
- `OHS_ENABLE_WORK_FLOW`(env `CUE_FLOW`) **기본 off** → 응답 `work_flow=None`
- **kill switch 실측**: 같은 저장 기록을 on(8001)/off(8003) 서버에서 GET → on은 흐름, off는 `null`
- `reviewed=False`(= `flow_service.LABELS_REVIEWED`)를 내려보내 화면이 '검수 전' 경고를 띄운다
- 실패는 전부 graceful degrade(흐름만 생략, 분석 응답 정상)

### 화면 원칙(전부 이유가 있다)

- **단계에 번호를 매기지 않는다**(사용자 합의) — '6단계 중 4단계'는 시간 추론이라 미측정 오류원
- **법정/권고를 배지로 가른다** — 섞으면 '해야 하는 것'과 '하면 좋은 것'이 구별되지 않는다
- **빈 칸에 사유를 쓴다** — '자료가 없음'과 '해당 없음'은 다른 말이고, 후자를 전자로 읽으면
  점검이 불필요한 것으로 오해한다
- **위험등급 색(amber/red) 미사용** — 같은 페이지 위험도 칩과 섞이면 흐름이 위험 판정으로 읽힌다

## 6. 앵커 정정 — 대안 칩만으로는 부족하다

**완전 오인식 26.7%** = RESOLVE가 준 1~4개 안에 정답이 아예 없는 경우. 칩만 있으면 4장 중 1장을 못 고친다.
→ 전체 127종 검색 선택기를 함께 넣었다.

```
GET /api/v1/flow/groups        선택기용 전체 목록 (LLM 0)
GET /api/v1/flow?group_key=…   해당 기인물의 흐름 (LLM 0). alternate= 로 되돌아갈 후보 유지
```

- 브라우저 실측: 칩으로 지게차→화물취급 교체 / 검색 '비계' 127→6종 → 달비계 선택 /
  '처음 인식으로 되돌리기' 원복 / 콘솔 에러 0
- **정정 이력 로그**: `from_group_key`를 함께 받아 무엇→무엇을 남긴다(그룹키만, 개인정보 없음).
  실사용 오인식률을 재는 재료
- 곁다리: `main.py`에 로깅 설정이 아예 없어 `app` 모듈의 `logger.info`가 전부 버려지고 있었다.
  `app` 네임스페이스만 좁게 INFO 핸들러를 붙였다(`OHS_LOG_LEVEL`)
- 곁다리: `_shared_reference_dir()`이 디렉토리 **존재만** 보고 반환해 빈 `backend/shared/reference`가
  리포 루트를 가로챘다(로컬 실행 시 분석 500). 모듈 파일 존재까지 확인하도록 수정

## 7. 주 기인물 선별은 손대지 않았다

RESOLVE가 주는 순서를 그대로 쓴다. "가장 두꺼운 흐름을 고른다" 같은 규칙은 그럴듯하지만
**측정된 바가 없다.** 그 전까지는 사용자 정정에 맡긴다.
