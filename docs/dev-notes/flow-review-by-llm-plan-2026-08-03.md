# 흐름 적합성을 GPT-5.6 Sol에게 검토받는 계획

작성 2026-08-03. 대상 = `flow_review_viewer.html`이 보여주는 흐름 2,206건(우산 16종 제외 후 111 그룹).

## 0. 왜 계획이 필요한가

전수 검수는 사람이 하기엔 양이 많다. 그런데 이 프로젝트에서 **LLM 판정을 사람이 뒤집은 일이
이미 있다** — 제52조는 3인 다수결이 EXEC로 몰았고 문언 소수의견이 옳았다. 그래서
"LLM에게 던진다"가 아니라 **"어떻게 물어야 틀린 답이 안 나오는가"**가 계획의 본체다.

핵심 결론 넷:

1. **"이거 맞아?"라고 묻지 않는다.** 우리 라벨을 보여주면 동의 편향이 생긴다. 라벨을 감추고
   **처음부터 다시 판정**시킨 뒤 대조한다. 불일치만 사람이 본다.
2. **질문을 둘로 쪼갠다.** 시점(어느 칸인가)과 적용(이 기인물에 붙는가)은 다른 질문이고,
   **여덟 번 난 버그는 전부 적용 쪽**이었다.
3. **적용은 조문 단위로 묻는다.** (조문, 그룹) 쌍마다 묻지 않는다. 조문 하나에 붙은 그룹
   목록을 통째로 주고 "이 중 적용 안 되는 것"을 고르게 한다 — 실제 버그가 났던 모양 그대로다.
4. **인용은 코드가 검증한다.** LLM 인용이 `fullText`에 글자 그대로 없으면 그 판정은 버린다.

## 1. 판정 단위 (실측)

| 단위 | 수 |
|---|---:|
| 그룹 | 111 |
| 항목(그룹 × 조문 × 칸) | 2,206 |
| **Q1 시점** — 서로 다른 (조문, 칸) | 1,142 → **조문 단위로 묶으면 683** |
| **Q2 적용** — 전용 아닌 (조문, 그룹) | 1,144 → **조문 단위로 묶으면 403** |

항목 2,206 중 절반은 같은 판정의 반복이다. 조문 단위로 묶으면 **683 + 403 = 1,086번**이면 된다.

Q2에서 가장 많이 반복되는 조문:

```
법 제29조 / 시행규칙 제26조 / 시행규칙 제27조    각 49개 그룹
제87~97조 (기계 일반기준 상속)                각 22개 그룹
```

이 25개 조문이 전체 반복의 대부분이다. **여기가 오부착이 나면 한 번에 수십 그룹이 틀린다.**
제38·39조가 126개 그룹에 붙었던 게 정확히 이 자리였다.

## 2. 방법 세 가지

### A안 — 그룹 단위 검토 (111회)

한 그룹의 6칸을 통째로 보여주고 "각 항목이 맞는 칸에 있나" 묻는다.

- 장점: 흐름 전체 맥락이 보인다. 칸 사이 선후관계를 볼 수 있는 유일한 방법.
- 단점: **우리 라벨을 보여주므로 동의 편향.** 그리고 같은 조문을 22번 다시 판정한다.
- 비용 ~$29 (Batch $15)

### B안 — 조문 단위 블라인드 재판정 + 적용 판정 ★ 추천

Q1과 Q2를 따로 돌린다. 우리 라벨을 **보여주지 않는다.**

- 장점: 편향 없음. 중복 제거로 싸다. **질문이 실제 버그 모양과 같다.**
- 단점: 칸 사이 선후관계는 못 본다(A안 소량 병행으로 보완).
- 비용 ~$23 (Batch **$12**)

### C안 — 전수 3인 패널

B안을 3회 독립 실행 후 다수결.

- 단점: 제52조에서 **다수결이 틀렸다.** 무작정 3배를 쓰는 건 그 실패를 3배로 재현할 수 있다.
- 대신 **불일치 건에만** 패널을 붙인다(B안 뒤 단계).

## 3. 추천 순서

```
0단계  정답지 프로브 8건            ~$1     ← Sol을 먼저 채점한다
1단계  Q1 시점 블라인드 재판정 683건  ~$4 (Batch)
2단계  Q2 적용 판정 403건           ~$4 (Batch)
3단계  인용 대조 (코드, 무료)
4단계  불일치 건만 3인 패널          ~$10
5단계  사람은 패널도 갈린 것만 본다
```

### 0단계가 제일 중요하다

**답을 이미 아는 8건을 먼저 던진다.** 맞히면 나머지를 맡기고, 틀리면 $12를 안 쓴다.

| 문항 | 정답 | 왜 정답인지 |
|---|---|---|
| 제52조가 신축공사에 자동 적용? | **아니오** | 조건부 의무. 사람이 3인 다수결을 뒤집었다 |
| 제38조가 모든 기인물에? | **아니오** | 별표 4의 13종 닫힌 목록 |
| 제39조가 모든 기인물에? | **아니오** | 제1항이 지목하는 호만 |
| 제133조가 승강기에? | **아니오** | "양중기(승강기는 제외한다)" |
| 제178조가 고소작업대에? | **아니오** | 고소작업대 조문이 아니다 |
| 제41조가 프레스에? | **아니오** | 차량계 대상 |
| 제86조가 승강기에? | **예** | 탑승 제한은 양중기 공통 |
| 제44조는 어느 칸? | **작업 전 + 작업 중** | 한 조문이 두 칸에 걸친다 |

여덟 문항 다 **"아니오"가 여섯**이다. 의도적이다 — Sol이 "그럴듯하면 예"라고 답하는
모델인지 먼저 본다.

## 4. 프롬프트

### Q1 — 시점 블라인드 재판정

```
system:
당신은 대한민국 산업안전보건기준에 관한 규칙을 읽는 사람이다.
조문 원문 하나를 읽고, 그 의무를 **언제** 이행해야 하는지 판정한다.

칸은 여섯이다:
  PLAN      계획·사전조사 — 작업을 계획하거나 착수 전 조사·서류를 만드는 시점
  ASSIGN    인적 배치·자격 — 누구를 배치·지정·교육하는가
  PRECHECK  작업 시작 전 점검 — 그날 작업을 시작하기 직전의 확인
  EXEC      작업 중 — 작업이 진행되는 동안 지켜야 하는 것
  POST      종료·이탈 — 작업을 마치거나 운전위치를 떠날 때
  PERIODIC  정기 점검 — 주기가 정해진 반복 점검

판정 규칙:
1. **제목이 아니라 본문으로 판단한다.** 제목이 '점검'이어도 본문이 작업 중 조치를
   말하면 EXEC다. 반대도 마찬가지다.
2. **한 조문이 여러 칸에 걸칠 수 있다.** 항이 다르면 시점이 다를 수 있다.
   해당하는 칸을 모두 낸다.
3. 각 칸마다 **그 시점을 가리키는 문구를 원문에서 그대로 인용**한다.
   요약하거나 바꿔 쓰지 않는다. 원문에 없는 글자를 쓰지 않는다.
4. 의무가 아니면(목적·정의·적용범위·적용제외) phases를 빈 배열로 낸다.
5. 확신이 없으면 confidence를 low로 낸다. 억지로 고르지 않는다.

법령을 해석해 새로운 의무를 만들지 않는다. 조문 번호를 추측하지 않는다.

user:
[조문] 제93조 방호장치의 해체 금지
[원문] {fullText}
```

**우리 라벨은 넣지 않는다.** 이것이 이 프롬프트의 핵심이다.

출력 스키마:

```json
{"type":"object","additionalProperties":false,
 "properties":{
   "phases":{"type":"array","items":{"type":"object","additionalProperties":false,
     "properties":{
       "phase":{"enum":["PLAN","ASSIGN","PRECHECK","EXEC","POST","PERIODIC"]},
       "quote":{"type":"string"},
       "why":{"type":"string"}},
     "required":["phase","quote","why"]}},
   "is_duty":{"type":"boolean"},
   "confidence":{"enum":["high","medium","low"]}},
 "required":["phases","is_duty","confidence"]}
```

### Q2 — 적용 판정 (제외 탐색 방향)

```
system:
당신은 대한민국 산업안전보건기준에 관한 규칙을 읽는 사람이다.
조문 하나와, 그 조문이 적용된다고 우리가 판단한 대상 목록을 준다.
그 목록에서 **이 조문이 적용되지 않는 대상**을 찾아낸다.

판정 규칙:
1. **조문 본문이 스스로 대상을 한정하는지 먼저 읽는다.** 규칙에는
   "양중기(승강기는 제외한다)"처럼 조문 안에서 대상을 좁히는 표현이 흔하다.
   그런 표현이 있으면 그것이 최우선이다.
2. 조문이 특정 기계·작업·물질을 지목하면, 지목되지 않은 대상은 제외 후보다.
3. 조문이 대상을 한정하지 않으면 제외하지 않는다. **한정하는 근거가 원문에 없는데
   "어울리지 않아 보인다"는 이유로 제외하지 않는다.**
4. 제외한다고 판정할 때마다 **그 근거 문구를 원문에서 그대로 인용**한다.
   인용할 문구가 없으면 제외하지 않는다.
5. 판단이 서지 않으면 unsure에 넣는다. exclude에 넣지 않는다.

법령을 해석해 새로운 의무를 만들지 않는다. 조문 번호를 추측하지 않는다.

user:
[조문] 제133조 정격하중 등의 표시
[원문] {fullText}
[우리가 적용된다고 본 대상 22종]
1. 양중기 > 크레인
2. 양중기 > 이동식 크레인
...
6. 양중기 > 승강기
...
```

출력 스키마:

```json
{"type":"object","additionalProperties":false,
 "properties":{
   "exclude":{"type":"array","items":{"type":"object","additionalProperties":false,
     "properties":{"target":{"type":"string"},"quote":{"type":"string"},"why":{"type":"string"}},
     "required":["target","quote","why"]}},
   "unsure":{"type":"array","items":{"type":"string"}},
   "scope_is_self_limited":{"type":"boolean"}},
 "required":["exclude","unsure","scope_is_self_limited"]}
```

### Q2 역방향 — 유지 변호

같은 403건을 **반대 방향**으로 한 번 더 돌린다. 이유는 이력에 있다 —
"안전한 기본값"을 지시하면 검증이 그 방향으로만 깎이는 **편향된 래칫**이 된다.

```
system:
조문 하나와 대상 목록을 준다. 각 대상에 대해 **이 조문이 적용되는 근거**를
원문에서 그대로 인용해 대라. 인용할 문구를 찾지 못한 대상은 no_basis에 넣는다.
근거를 만들어내지 않는다. 원문에 없는 글자를 쓰지 않는다.
```

**제외 탐색의 `exclude`와 유지 변호의 `no_basis`가 겹치는 것** = 신뢰도 높은 오부착.
한쪽에만 나온 것 = 사람이 볼 것.

## 5. 코드가 하는 일 (LLM에게 맡기지 않는다)

1. **인용 대조** — 응답의 모든 `quote`를 `fullText`에서 정규화 후 검색. 없으면 그 판정 폐기.
   정규화는 공백만 제거한다. **조사·어미는 절대 건드리지 않는다**(기존 `build_article_phases.py` 규칙).
2. **대조표 생성** — Q1 응답 vs 현재 라벨, Q2 `exclude` vs 현재 배선.
3. **불일치만 4단계로** 올린다.
4. **적용 결과는 `human_review.json`을 거친다.** LLM 판정이 데이터를 직접 덮어쓰지 않는다.

## 7. 이 방법으로 잡히지 않는 것 (미리 적어둔다)

- **칸 사이 선후관계.** 조문 단위로 물으면 "계획 다음에 이 점검이 오는 게 맞나"는 못 본다.
  A안을 20그룹 정도만 병행해 보완한다(~$5).
- **빠진 조문.** 이 계획은 붙어 있는 것만 검증한다. 없는 것을 찾는 건 다른 작업이고,
  조문 번호 추측 금지 규칙과 충돌하므로 별도 설계가 필요하다.
- **가이드(권고) 214건 · 별표/고시 항목.** 조문 원문이 없어 Q1 프롬프트가 그대로 안 먹는다.
  2차로 분리한다.
- **Sol이 우리 배선 의도를 모른다는 점.** 이름매칭으로 붙인 94건은 불일치가 많이 날 것이다.
  그게 목적이다 — 이름만 같아서 붙은 것을 찾는 게 이 검토의 노림수다.
